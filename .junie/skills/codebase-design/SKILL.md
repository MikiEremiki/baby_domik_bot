# Codebase Design

Проектируй **глубокие модули**: много поведения за маленьким интерфейсом, размещённым на чистом шве, тестируемым через этот интерфейс. Используй этот язык и эти принципы везде, где код проектируется или реструктуризируется. Цель — рычаг для вызывающих, локальность для поддерживающих и тестируемость для всех.

## Словарь

Используй эти термины точно: не заменяй на "компонент", "сервис", "API" или "границу".

**Модуль**: всё, что имеет интерфейс и реализацию. Намеренно агностичен к масштабу: функция, класс, пакет или сквозной срез. _Избегай_: unit, component, service.

**Интерфейс**: всё, что вызывающий должен знать для правильного использования модуля: тип сигнатуры, но также инварианты, ограничения порядка, режимы ошибок, необходимая конфигурация и характеристики производительности. _Избегай_: API, signature (слишком узко, они относятся только к типизированной поверхности).

**Реализация**: то, что внутри модуля, его тело кода. Отлично от **Адаптера**: вещь может быть маленьким адаптером с большой реализацией (Postgres репозиторий) или большим адаптером с маленькой реализацией (in-memory фейк).

**Глубина**: рычаг на интерфейсе. Количество поведения, которое вызывающий (или тест) может использовать за единицу изученного интерфейса. Модуль **глубокий**, когда много поведения за маленьким интерфейсом, **плоский**, когда интерфейс почти так же сложен, как реализация.

**Шов** _(Michael Feathers)_: место, где можно изменить поведение без редактирования в этом месте; _локация_, где живёт интерфейс модуля. Где разместить шов — это своё решение дизайна, отличное от того, что за ним. _Избегай_: boundary (перегружено DDD bounded context).

**Адаптер**: конкретная вещь, которая удовлетворяет интерфейс на шве. Описывает _роль_ (какую слот заполняет), не substance (что внутри).

**Рычаг**: то, что получают вызывающие от глубины. Больше возможностей за единицу изученного интерфейса. Одна реализация окупается на N вызывающих и M тестах.

**Локальность**: то, что получают поддерживающие. Изменение, баги, знания и верификация концентрируются в одном месте, а не распространяются среди вызывающих. Исправь один раз, исправлено везде.

## Глубокий vs плоский

**Глубокий модуль** = маленький интерфейс + много реализации:

```
┌─────────────────────┐
│   Маленький Интерфейс  │  ← Мало методов, простые параметры
├─────────────────────┤
│                     │
│  Глубокая Реализация  │  ← Сложная логика скрыта
│                     │
└─────────────────────┘
```

**Плоский модуль** = большой интерфейс + мало реализации (избегай):

```
┌─────────────────────────────────┐
│       Большой Интерфейс         │  ← Много методов, сложные параметры
├─────────────────────────────────┤
│  Тонкая Реализация              │  ← Просто пропускает
└─────────────────────────────────┘
```

При проектировании интерфейса спроси:
- Могу ли я уменьшить количество методов?
- Могу ли я упростить параметры?
- Могу ли я скрыть больше сложности внутри?

## Принципы

- **Глубина — свойство интерфейса, не реализации.** Глубокий модуль может быть внутренне составлен из маленьких, мокабельных, заменяемых частей; они просто не часть интерфейса.
- **Тест на удаление.** Представь удаление модуля. Если сложность исчезла, это был прокси. Если сложность появилась у N вызывающих, он оправдывал себя.
- **Интерфейс — это поверхность для тестов.** Вызывающие и тесты пересекают один и тот же шов. Если ты хочешь тестировать _за_ интерфейсом, модуль, вероятно, неправильной формы.
- **Один адаптер означает гипотетический шов. Два адаптера — настоящий.** Не вводите шов, если ничего не варьируется.

## Проектирование для тестируемости

Хорошие интерфейсы делают тестирование естественным:

1. **Принимай зависимости, не создавай их.**

   ```python
   # Тестируемо
   def process_order(order, payment_gateway): ...

   # Сложно тестировать
   def process_order(order):
       gateway = StripeGateway()
   ```

2. **Возвращай результаты, не производи побочные эффекты.**

   ```python
   # Тестируемо
   def calculate_discount(cart) -> Discount: ...

   # Сложно тестировать
   def apply_discount(cart) -> None:
       cart.total -= discount
   ```

3. **Маленькая поверхность.** Меньше методов = меньше тестов нужно. Меньше параметров = проще настройка теста.

## Отношения

- **Модуль** имеет ровно один **Интерфейс** (поверхность, которую он представляет вызывающим и тестам).
- **Глубина** — свойство **Модуля**, измеряемое против его **Интерфейса**.
- **Шов** — где живёт **Интерфейс** **Модуля**.
- **Адаптер** сидит на **Шве** и удовлетворяет **Интерфейс**.
- **Глубина** производит **Рычаг** для вызывающих и **Локальность** для поддерживающих.

## Отклонённые формулировки

- **Глубина как отношение строк реализации к строкам интерфейса** (Ousterhout): поощряет надувание реализации. Мы используем глубину-как-рычаг.
- **"Интерфейс" как ключевое слово TypeScript `interface` или публичные методы класса**: слишком узко: интерфейс здесь включает каждый факт, который вызывающий должен знать.
- **"Граница"**: перегружена DDD bounded context. Говори **шов** или **интерфейс**.
