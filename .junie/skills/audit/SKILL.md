# Audit Check

Независимый аудит проекта по шаблону из `checklists/`. В отличие от `/task`, который проверяет конкретную задачу, `/audit` сканирует весь проект или выбранную часть проекта по заданному шаблону.

## Как это работает

1. Пользователь вызывает `/audit` с указанием типа аудита и (опционально) области
2. Агент читает шаблон из `checklists/`
3. Агент сканирует проект по всем пунктам чек-листа
4. Создаётся отчёт `reports/YYYY-MM-DD_audit-type.md`
5. Обновляется статистика `STATISTICS.md`

**Жизненный цикл:**
- Шаблоны в `checklists/` — не меняются, служат эталоном
- Каждый запуск создаёт отчёт в `reports/` — история не теряется
- Статистика показывает, какие проблемы встречаются чаще

## Когда использовать

- Пользователь хочет проверить весь проект по определённому виду аудита
- Пользователь явно вызывает `/audit`
- Периодическая проверка качества кода (например, раз в месяц)
- Перед релизом или крупным рефакторингом

## Формат вызова

```
/audit [тип] [--path путь]
```

**Параметры:**

| Параметр | Описание | Пример |
|----------|----------|--------|
| `тип` | Номер или название аудита из `checklists/` | `12`, `SOLID`, `security`, `type-hints` |
| `--path` | Опционально: ограничить область проверки | `--path src/handlers/`, `--path src/api/` |

**Примеры:**

```
/audit SOLID
/audit 12
/audit security --path src/api/
/audit type-hints --path src/handlers/
/audit frontend --path templates/
```

## Доступные типы аудитов

| Команда | Шаблон | Описание |
|---------|--------|----------|
| `/audit security` | `01_SECURITY_AUDIT.md` | Безопасность: XSS, SQL-инъекции, file upload |
| `/audit test-coverage` | `02_TEST_COVERAGE_AUDIT.md` | Тестовое покрытие: gaps, edge-кейсы |
| `/audit performance` | `03_PERFORMANCE_AUDIT.md` | Производительность: время расчета, оптимизатор |
| `/audit type-hints` | `04_TYPE_HINTS_AUDIT.md` | Типизация: Dict→Dataclass, return type hints |
| `/audit api-design` | `05_API_DESIGN_AUDIT.md` | API-дизайн: REST, пагинация, error responses |
| `/audit frontend` | `06_FRONTEND_ARCHITECTURE_AUDIT.md` | Frontend: Jinja2-шаблоны, CSS, a11y, адаптивность |
| `/audit error-handling` | `07_ERROR_HANDLING_AUDIT.md` | Обработка ошибок: exception handler, логирование |
| `/audit documentation` | `08_DOCUMENTATION_AUDIT.md` | Документация: docstrings, README, CHANGELOG |
| `/audit dependency` | `09_DEPENDENCY_AUDIT.md` | Зависимости: устаревшие пакеты, лицензии |
| `/audit configuration` | `10_CONFIGURATION_AUDIT.md` | Конфигурация: settings.json, магические числа |
| `/audit i18n` | `11_I18N_AUDIT.md` | Интернационализация: локализация, дата/время |
| `/audit solid` | `12_SOLID_AUDIT.md` | SOLID-принципы: DRY, Single Responsibility |
| `/audit telegram-ui` | `13_TELEGRAM_UI_AUDIT.md` | Telegram UI: клавиатуры, inline-кнопки, сообщения |

## Процесс выполнения

**1. Определите область проверки**
- Если `--path` указан — проверяйте только эту папку/файл
- Если `--path` не указан — проверяйте весь проект (`src/`, `templates/`, `test/`)

**2. Прочитайте шаблон аудита**
- Откройте соответствующий файл из `checklists/`
- Изучите все пункты чек-листа

**3. Выполните проверку по каждому пункту**
- Для каждого пункта чек-листа проведите поиск в коде
- Используйте `grep_search`, `glob_search` для поиска паттернов
- Используйте `jbcontext search` для семантического поиска
- Фиксируйте найденные проблемы с файлами и строками

**4. Создайте отчёт**
- **Путь:** `.junie/audit/reports/YYYY-MM-DD_audit-type.md`
- **Шаблон:** `.junie/audit/REPORT_TEMPLATE.md`
- **Содержимое:** Метаданные, сработавшие пункты, найденные проблемы, рекомендации

**5. Обновите статистику**
Обновите `.junie/audit/STATISTICS.md`:

- **Общая сводка:** Увеличьте счётчики: всего отчётов, отчётов с проблемами, всего проблем
- **По видам аудитов:** Найдите строку с соответствующим видом аудита (например, `SOLID (DRY)`) и увеличьте счётчик "Сработало раз". Если строки нет — добавьте новую
- **По частоте проблем:** Для каждой найденной проблемы увеличьте счётчик в таблице "По частоте проблем". Если проблема новая — добавьте строку
- **По файлам (top-10):** Для каждого файла с проблемой увеличьте счётчик. Пересортируйте таблицу по убыванию, оставьте top-10
- **Временная шкала:** Найдите текущий месяц (например, `2026-10`) и увеличьте счётчики "Отчётов" и "Проблем". Если месяца нет — добавьте новую строку
- **Выводы:** Если это первый отчёт по данному виду аудита, добавьте краткий вывод: сколько проблем, какие наиболее критичные

> **Важно:** Не меняйте раздел "Рекомендации мини-аудита" — он обновляется только `/task-check`.

| Приоритет | Проблема | Файл | Что сделать |

## Примеры использования

### Полный аудит SOLID всего проекта

Пользователь: `/audit solid`

Результат: Агент проверяет весь проект по шаблону `12_SOLID_AUDIT.md`, создаёт отчёт `reports/2026-10-05_solid-audit.md` с найденными проблемами DRY, Single Responsibility и т.д.

### Аудит безопасности API

Пользователь: `/audit security --path src/api/`

Результат: Агент проверяет только папку `src/api/` по шаблону `01_SECURITY_AUDIT.md`, создаёт отчёт с уязвимостями XSS, SQL-инъекциями, file upload.

### Аудит типизации хендлеров

Пользователь: `/audit type-hints --path src/handlers/`

Результат: Агент проверяет `src/handlers/` по шаблону `04_TYPE_HINTS_AUDIT.md`, находит Dict[str, Any] вместо dataclass, отсутствие return type hints.

### Периодический аудит веб-части

Пользователь: `/audit frontend --path templates/`

Результат: Агент проверяет `templates/` по шаблону `06_FRONTEND_ARCHITECTURE_AUDIT.md`, находит DRY-нарушения в Jinja2-шаблонах, проблемы с CSS.

## Сравнение с `/task`

| Аспект | `/task` | `/audit` |
|--------|---------|----------|
| **Цель** | Проверка конкретной задачи | Проверка всего проекта или части |
| **Когда** | Перед реализацией задачи | Периодически, перед релизом |
| **Область** | Затронутые файлы задачи | Весь проект или выбранная папка |
| **Шаблоны** | DRY, edge-кейсы, регрессии | Любой из 12 шаблонов в `checklists/` |
| **Отчёт** | `reports/YYYY-MM-DD_task-name.md` | `reports/YYYY-MM-DD_audit-type.md` |

## Создание плана из отчёта

После аудита, если найдены проблемы, предложите пользователю создать план устранения.

**Когда предлагать:**
- В отчёте найдено 2+ проблемы
- Пользователь не отклонил предложение

**Как создать план:**

1. **Прочитайте отчёт** из `reports/YYYY-MM-DD_audit-type.md`
2. **Создайте черновик плана** в `.junie/plans/fix-audit-[тип].md` по формату ниже
3. **Покажите план пользователю** и спросите о правках
4. **После одобрения** — приступайте к реализации по шагам

**Формат плана:**

```markdown
# Исправление: [Тип аудита]

## Источник
- **Отчёт:** `reports/YYYY-MM-DD_audit-type.md`
- **Дата аудита:** YYYY-MM-DD
- **Количество проблем:** N

## Delivery Steps

###   Step 1: [Название проблемы 1] 🔴
- **Файл:** `path/to/file.py:123`
- **Что исправить:** Описание из отчёта
- **Приоритет:** 🔴 Высокий

###   Step 2: [Название проблемы 2] 🟡
- **Файл:** `path/to/file2.py:456`
- **Что исправить:** Описание из отчёта
- **Приоритет:** 🟡 Средний

...

## Testing
- После каждого шага проверить, что ничего не сломано
- Запустить существующие тесты
```

**Правила формирования плана:**
- Каждая проблема из отчёта → один шаг плана
- Шаги отсортированы по приоритету: 🔴 → 🟡 → 🟢
- Если проблемы затрагивают один файл — сгруппируйте их в один шаг
- Добавьте секцию Testing с проверками

**Пример:**

Пользователь: `/audit solid`
Агент: *[аудит]* → отчёт с 10 проблемами
Агент: "Найдено 10 проблем. Создать план устранения?"
Пользователь: "Да"
Агент: *[создаёт план]* → `.junie/plans/fix-audit-solid.md`
Агент: "План создан. 10 шагов, отсортированы по приоритету. Что хотите изменить?"
Пользователь: "Убери проблемы 8 и 10, они не критичные"
Агент: *[корректирует план]* → 8 шагов
Пользователь: "Ок, приступай"
Агент: *[выполняет по шагам]*

## Советы

- **Регулярные аудиты:** Запускайте `/audit solid` и `/audit type-hints` после каждой крупной фичи
- **Перед релизом:** Запустите `/audit security` и `/audit test-coverage`
- **Точечные проверки:** Используйте `--path` для быстрой проверки конкретной области
- **Сравнение отчётов:** Откройте `STATISTICS.md` для анализа трендов
- **Планы из отчётов:** После аудита всегда предлагайте создать план устранения
