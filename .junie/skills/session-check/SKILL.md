# Session Check

Помогает решить, когда продолжить существующую сессию Junie, а когда начать новую. Используется вместе с системой аудитов для поддержания качества кода.

## Когда использовать

- Пользователь не уверен, начать новую сессию или продолжить текущую
- Пользователь явно вызывает `/session-check`
- Перед началом новой задачи в существующей сессии

## Правила решения

### Начать новую сессию, когда:

| Правило | Пример |
|---------|--------|
| **Новая область кода** | Предыдущая задача — handlers бота, новая — FastAPI веб-часть |
| **Исправление бага** | Нужен чистый контекст, чтобы не мешать рабочему коду |
| **Разные виды аудитов** | Предыдущая — SOLID, новая — Security |
| **Сессия > 20 сообщений** | Контекст начинает теряться, лучше начать заново |
| **После rollback'а** | Если код был откатен, новая сессия не будет знать о старых изменениях |

### Продолжить сессию, когда:

| Правило | Пример |
|---------|--------|
| **Та же область кода** | Продолжаем работу над handlers/, теми же файлами |
| **Доработка предыдущей задачи** | "Ещё немного подправь то, что мы только что сделали" |
| **Те же виды аудитов** | Продолжаем исправлять нарушения DRY |
| **Сессия < 15 сообщений** | Контекст ещё свежий |
| **Зависимость от предыдущего** | Новая задача строится на результатах предыдущей |

## Анализ

Когда пользователь вызывает этот скилл, проанализируйте:

1. **Контекст текущей сессии** — что уже было сделано
2. **Область новой задачи** — какие файлы и модули затронуты
3. **Пересечение с предыдущими задачами** — есть ли зависимость
4. **Длина сессии** — сколько сообщений уже было

## Формат результата

```markdown
## Рекомендация по сессии

### Анализ
- Текущая сессия: [количество] сообщений, [тема]
- Новая задача затрагивает: [файлы/модули]
- Пересечение с текущей сессией: [есть/нет]

### Рекомендация
✅ **Продолжить сессию** — [обоснование]
или
🔄 **Начать новую сессию** — [обоснование]

### Если новая сессия
Вот контекст, который нужно передать:
- [список ключевых фактов из текущей сессии]
```

## Защита от регрессий

### Проблема

Вы исправили баг → код работает → новая задача → Junie изменил тот же файл → баг вернулся → нужно объяснять "мы это только что починили".

### Решение

После исправления бага попросите пользователя вызвать `/task-check --regression` для фиксации исправления.

Регрессионные заметки хранятся в `.junie/audit/REGRESSIONS.md`.

## Примеры использования

### Длинная сессия с handlers/

Пользователь: `/session-check Добавить валидацию номера телефона в бронирование`

Результат:
```
🔄 **Начать новую сессию** — текущая сессия слишком длинная (25 сообщений).
Контекст для новой сессии:
- Валидация телефонов через custom_filters/
- Хендлеры в src/handlers/reserve_hl.py
- Клавиатуры через src/utilities/utl_kbd.py
```

### Исправление бага

Пользователь: `/session-check Исправить баг — цена становится отрицательной при промокоде`

Результат:
```
🔄 **Начать новую сессию** — исправление бага требует чистого контекста.
После исправления запустите /task-check --regression
```

### Доработка текущей задачи

Пользователь: `/session-check Поменять текст кнопки на «Выбрать сеанс»`

Результат:
```
✅ **Продолжить сессию** — задача связана с предыдущей, контекст свежий.
```

## Интеграция с аудитами

### При начале новой сессии

1. Запустите `/session-check`
2. Если агент рекомендует новую сессию — скопируйте контекст
3. В новой сессии запустите `/task-check`
4. Агент проверит затронутые виды аудитов и регрессии

### При продолжении сессии

1. Агент уже знает контекст
2. Запустите `/task-check` для проверки новых нарушений
3. Агент учтёт предыдущие изменения в сессии

## Чек-лист перед началом работы

- [ ] Запустил `/session-check`?
- [ ] Если новая сессия — передал контекст из предыдущей?
- [ ] Запустил `/task-check`?
- [ ] Проверил `.junie/audit/REGRESSIONS.md` на активные регрессии?
- [ ] Если задача затрагивает файлы с регрессиями — учёл предупреждения?
