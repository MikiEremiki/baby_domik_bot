# Task Check

Проверка задачи перед реализацией. Работает для задач любого размера: от мелкой правки до крупной фичи.

Рекомендует, нужен ли `/to-spec` для создания спецификации.

## Как это работает

Каждый аудит создаёт **отчёт** в `.junie/audit/reports/`. Отчёты накапливаются и формируют **статистику** в `.junie/audit/STATISTICS.md`.

**Жизненный цикл:**
1. Пользователь вызывает `/task-check` с описанием задачи
2. Агент проверяет задачу по шаблонам из `checklists/`
3. Создаётся отчёт `reports/YYYY-MM-DD_task-name.md`
4. Обновляется сводная статистика `STATISTICS.md`
5. Агент рекомендует, нужен ли `/to-spec`

## Когда использовать

- Пользователь описывает новую задачу и просит проверить, прежде чем реализовывать
- Пользователь явно вызывает `/task-check`
- Задача затрагивает существующие файлы, и нужно проверить дублирование кода

## Режимы

### Стандартный (по умолчанию)

**1. Определите затронутые файлы**
- Какие файлы будут изменены или созданы
- Не затрагивает ли задача файлы с активными регрессиями

**2. Чек-лист DRY (дублирование кода)**
- [ ] Есть ли уже похожая логика в проекте?
- [ ] Можно ли использовать существующую утилиту/функцию вместо написания новой?
- [ ] Не создаёт ли задача новый дубликат существующего паттерна?

**3. Edge-кейсы (baby_domik_bot)**
- [ ] Пустые данные: пустой список сеансов, None/null пользователь
- [ ] Граничные значения: нулевая цена билета, 0 мест, очень длинное сообщение
- [ ] Ошибки ввода: некорректный callback_data, валидация пользовательского ввода
- [ ] Состояние системы: недоступная БД, таймаут Google Sheets, NATS-сообщение без обработчика
- [ ] Конкурентные операции: двойное бронирование одного места

**4. Регрессии**
- Откройте `.junie/audit/REGRESSIONS.md`
- Проверьте, не затрагивает ли задача файлы с активными регрессионными заметками
- Если да — выдайте предупреждение

**5. Отчёт с вариантами решений**

```markdown
## Аудит задачи: [название]

### Затронутые файлы
- `src/handlers/reserve_hl.py` — изменение логики бронирования
- ⚠️  Внимание: файл имеет активную регрессионную заметку

### Чек-лист DRY
- [x] Похожая логика найдена: `src/utilities/utl_kbd.py` — можно использовать
- [x] Дублирование не обнаружено

### Edge-кейсы
- [x] Пустой список сеансов — обработано
- [ ] Таймаут Google Sheets — не обработано, нужно добавить retry

### Варианты решения

**Вариант А: Использовать существующую утилиту**
- ➕ Плюсы: Нет дублирования, уже протестировано
- ➖ Минусы: Требует изменения сигнатуры функции
- Рекомендация: ✅ Выбрать этот вариант

### Итог
Рекомендую Вариант А. Перед реализацией добавьте обработку таймаута.
```

**6. Оценка: нужен ли более глубокий аудит?**

| Критерий | Условие | Балл |
|----------|---------|------|
| **Количество файлов** | ≥ 3 файла | +1 |
| **Найденные проблемы** | ≥ 2 проблемы или 1 критичная | +1 |
| **Регрессионный риск** | Файл с активной регрессией затрагивается | +1 |
| **Сложность задачи** | Новая фича, рефакторинг, изменение формата данных | +1 |

| Баллы | Рекомендация |
|-------|-------------|
| **0–1** | Мини-аудит достаточен |
| **2** | Рекомендую `--full` |
| **3–4** | Рекомендую `--full` + `--regression` |

**7. Рекомендация: нужна ли спецификация?**

| Критерий | Условие | Рекомендация |
|----------|---------|-------------|
| **Количество файлов** | ≥ 3 файла | ⚠️ Рекомендую `/to-spec` |
| **Изменение нескольких модулей** | handlers + БД или NATS + FastAPI | ⚠️ Рекомендую `/to-spec` |
| **Новая подсистема** | Новый тип хендлера, новый воркер | 🔴 Обязательно `/to-spec` |
| **Мелкая правка** | 1-2 файла, очевидное изменение | ✅ Спецификация не нужна |

**8. Создание отчёта**
- **Путь:** `.junie/audit/reports/YYYY-MM-DD_task-name.md`
- **Шаблон:** `.junie/audit/REPORT_TEMPLATE.md`

**9. Обновление статистики**
Обновите `.junie/audit/STATISTICS.md`.

### Полный режим (`--full`)

Всё из стандартного режима + дополнительно:

- Сопоставление с видами аудитов (`.junie/audit/terms/AUDIT_TYPES.md`)
- Проверка документации (`docs/`)
- План реализации с учётом аудитов

### Регрессионный режим (`--regression`)

После исправления бага фиксирует исправление:

```markdown
## Активные
- **reserve_hl.py:123** — Guard clause для пустого списка сеансов (исправлено 2026-10-06)
  - Что: Исправлено бронирование при пустом списке сеансов
  - Почему важно: Без этого бот падает с IndexError
  - Как проверить: Передать пустой список → должно вернуть сообщение, не падать
```

## Примеры использования

### Мелкая задача

Пользователь: `/task-check Добавить кнопку «Назад» в меню бронирования`

Результат: Краткий отчёт с проверкой DRY, edge-кейсов + рекомендация.

### Средняя задача

Пользователь: `/task-check --full Добавить новый тип билета «Семейный»`

Результат: Полный отчёт + рекомендация `/to-spec`.

### После исправления бага

Пользователь: `/task-check --regression Исправлен баг: двойное бронирование одного места`

Результат: Регрессионная заметка в REGRESSIONS.md + отчёт.
