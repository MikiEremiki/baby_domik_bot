# Инструкции и операционные правила для AI-агентов (AGENT.md)
## BabyDomikBot

Документ содержит обязательные операционные правила («если ..., то ...»), инварианты разработки и навигатор по справочной документации проекта.

---

### 1. Рабочий процесс (Workflow)

**Полная памятка по воркфлоу:** [`WORKFLOWS.md`](WORKFLOWS.md) — основной поток, расширенный конвейер, обучение, управление сессиями.

**Мгновенные правки:** если задача затрагивает **1 файл** и решение **очевидно** (изменить текст, цвет, опечатку) — просто скажите Junie. Никаких скиллов, проверок и ревью не нужно.

**Простой режим:** если задача затрагивает **2-3 файла** и решение **ясно** (добавить валидацию, поправить формулу, новый эндпоинт) — `/task-check` → `/implement` → `/code-review`. Без grill и spec, но с проверкой DRY, edge-кейсов и ревью.

**Основной поток: идея → релиз**

1. **Не знаешь, что делать?** — `/ask-junie` подскажет, какой скилл использовать.
2. **Задача неоднозначна?** — `/grill-with-docs` уточнит через опрос, обновив `docs/GLOSSARY.md` и ADR.
3. **Спецификация** — `/to-spec` превратит обсуждение в `.scratch/SPEC.md`.
4. **Проверь задачу** — `/task-check` проверит DRY, edge-кейсы, регрессии.
5. **Реализация** — `/implement` структурирует: контекст → план → код.
6. **Ревью** — `/code-review` проведёт двухосный ревью: стандарты + спецификация.
7. **Коммит** — `/commits` с правильным форматом.

**Спецсценарии:**

- **Баг?** — `/diagnosing-bugs` для систематической диагностики.
- **Новая сессия?** — `/session-check` решит, продолжить или начать новую.
- **Аудит проекта?** — `/audit [тип]` для периодической проверки.
- **Синхронизация?** — `/audit-sync` после крупного рефакторинга.

### 3. Операционные инструкции («Если ..., то ...»)

#### 3.1. Разработка handlers/ (python-telegram-bot)
- **Если создаешь новый обработчик:**
  - Состояния (states) определяй в `src\conv_hl\` с суффиксом `_conv_hl.py`.
  - Бизнес-логику выноси в `src\handlers\` с суффиксом `_hl.py`.
  - Регистрируй обработчик в `src\setup_bot_handlers.py`.
- **Если создаёшь клавиатуру:**
  - Используй функции из `src\utilities\utl_kbd.py`.
  - Для кнопок "Назад" и "Отмена" используй `add_btn_back_and_cancel`.
- **Если добавляешь middleware:**
  - Сохраняй существующие middleware: `add_db_handlers_middleware`, `add_glob_on_off_middleware`, `add_user_status_middleware`, `add_reserve_check_middleware`, `add_tg_update_logging_middleware`.

#### 3.2. Разработка FastAPI (routes, schemas, webhooks)
- **Если добавляешь или изменяешь эндпоинты:**
  - Валидируй входные параметры через Pydantic-схемы в `src\api\web\schemas.py`.
  - Размещай роутеры в `src\api\web\routes\`: `api.py` (вебхуки), `auth.py` (Telegram Login), `booking.py` (бронирование), `pages.py` (HTML-страницы).
- **Если работаешь с вебхуками YooKassa:**
  - Вебхук приходит на `POST /yookassa`, публикуется в NATS тему `yookassa`.
  - Обработка в `src\handlers\hooks\yookassa_hl.py`: статус `succeeded` → обновление БД и Google Sheets.

#### 3.3. Работа с NATS (broker_nats.py, воркеры)
- **Если публикуешь сообщение в NATS:**
  - Используй FastStream для публикации в соответствующую тему: `yookassa`, `gspread`, `sales`.
  - Убедись, что стрим `baby_domik` существует (скрипт `src/api/nats_migrate.py`).
- **Если создаёшь нового воркера:**
  - Подписывайся на тему с durable-именем.
  - Публикуй результаты в соответствующую тему: `gspread_failed`, `schedule_sync_result`, `sales_report`.
- **Если изменяешь имена субъектов/стримов:**
  - Синхронизируй publisher и consumer на обеих сторонах.

#### 3.4. Работа с БД (SQLAlchemy, Alembic)
- **Если работаешь с БД:**
  - Всегда используй `AsyncSession`.
  - Новые CRUD-методы добавляй в `src\db\db_postgres.py`.
  - Модели описывай в `src\db\models.py` с использованием SQLAlchemy 2.0 style.
  - Используй `lazy='raise'` для явной загрузки связанных сущностей (`joinedload`/`selectinload`).
- **Если изменяешь модели:**
  - Создай миграцию Alembic: `alembic -c "config\alembic.ini" revision --autogenerate -m "description"`.

#### 3.5. Google Sheets (gspread, rate limits)
- **Если записываешь в Google Sheets:**
  - Используй асинхронную запись через NATS (`gspread_pub.py` → `gspread_worker.py`).
  - Не выполняй синхронные вызовы gspread в обработчиках бота.
- **Если читаешь из Google Sheets:**
  - Используй команды `/update_*` для синхронизации данных в БД.
  - Маппинг `RANGE_NAME` задаёт именованные вкладки/диапазоны.

#### 3.6. Синхронизация документации (Definition of Done)
- **Если добавил или изменил эндпоинты API:** → обнови `docs/ARCHITECTURE.md`.
- **Если изменил архитектуру слоёв или файловую структуру:** → обнови `docs/ARCHITECTURE.md`.
- **Если принял новое архитектурное решение:** → зафиксируй новый ADR в `docs/ADR.md`.
- **Если ввёл новый термин или изменил существующий:** → обнови `docs/GLOSSARY.md`.

### 4. Базовые правила работы Junie

- **ОС:** Windows. Используй PowerShell-команды и обратные слэши `\` в путях.
- **Тесты:** `python -m pytest -q` из корня проекта; для интеграционных потоков — `docker-compose`.
- **Минимальные изменения:** правь только то, что требуется задачей; не трогай deployment-файлы без необходимости.
- **План реализации:** перед написанием кода предложи детальный план и согласуй его с пользователем.
- **Стиль:** PEP 8, типизация по возможности; секреты и пути — только в `config\` и `.env`, не хардкодить.
- **Логи:** через утилиты `src\log` (именованные логгеры: `bot.webhook`, `bot.timeweb_api` и др.).
- **Submission:** при изменениях Python-кода — запускать pytest; для правок только документации сборка/тесты не требуются.
