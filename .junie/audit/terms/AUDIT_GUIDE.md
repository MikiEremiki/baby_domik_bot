## 🔴 Высокий приоритет

<a id="security"></a>
### 1. Аудит безопасности (Security Audit)

**Цель:** Найти уязвимости, которые могут быть использованы для несанкционированного доступа, повреждения данных или компрометации системы.

**Когда запускать:**
- Перед релизом или деплоем в продакшен
- После добавления новых API-эндпоинтов
- После изменения логики обработки платежей
- Раз в квартал как плановая проверка

**Что именно искать:**

| Категория | Паттерн поиска | Пример проблемы |
|-----------|----------------|-----------------|
| **SQL-инъекции** | f-strings/concat в SQL-запросах | `f"SELECT * FROM tickets WHERE id = {ticket_id}"` |
| **XSS в Telegram** | `parse_mode="HTML"` с пользовательскими данными | Вывод имени пользователя без экранирования в HTML-сообщении |
| **CSRF в FastAPI** | Отсутствие CSRF-токенов в формах | Веб-бронирование без защиты от CSRF |
| **Информационное раскрытие** | `traceback.format_exc()` в ответах API | Stack trace в JSON-ответе клиенту |
| **Секреты в коде** | `token = "..."`, `api_key = "..."` | Токены бота, YooKassa, Timeweb в коде |
| **Аутентификация** | Отсутствие проверки прав доступа | Админские эндпоинты без авторизации |

**Инструменты:**
- `bandit src/` — статический анализ Python на уязвимости
- `pip-audit` — проверка зависимостей на известные CVE
- Ручной просмотр: `grep -r "password\|secret\|token" src/`

**Критерий "аудит пройден":**
- Нет критических уязвимостей (SQL-инъекции, XSS)
- Все секреты вынесены в `config/settings.yml` и `.env`
- Админские эндпоинты защищены `filter_admin`

<a id="test-coverage"></a>
### 2. Аудит тестового покрытия (Test Coverage Audit)

**Цель:** Убедиться, что критические пути кода покрыты тестами.

**Когда запускать:**
- Перед крупным рефакторингом
- После добавления новой фичи
- Когда процент покрытия падает ниже 70%

**Что именно искать:**

| Категория | Что измерять | Пример проблемы |
|-----------|--------------|-----------------|
| **Процент покрытия** | `coverage run -m pytest; coverage report` | Покрытие < 70% |
| **Критические пути** | Обработка платежей, бронирование | `reserve_hl.py` без тестов |
| **Edge-кейсы** | Пустые данные, таймауты | Нет тестов на недоступную Google Sheets |
| **Интеграционные тесты** | Полный поток: бронирование → оплата → уведомление | Только unit-тесты |

**Инструменты:**
- `coverage run -m pytest; coverage html` — HTML-отчёт
- `pytest --cov-fail-under=70` — провал при низком покрытии

**Критерий "аудит пройден":**
- Покрытие ≥ 70% для бизнес-логики
- Все критические пути покрыты тестами
- Есть интеграционные тесты на полный поток бронирования

<a id="performance"></a>
### 3. Аудит производительности (Performance Audit)

**Цель:** Найти узкие места, замедляющие работу бота и API.

**Когда запускать:**
- При жалобах на медленную работу
- Перед ожидаемым ростом нагрузки
- После добавления вычислительно сложных операций

**Что именно искать:**

| Категория | Что измерять | Пример проблемы |
|-----------|--------------|-----------------|
| **NATS очереди** | Задержка обработки сообщений | Воркеры не успевают обрабатывать |
| **Google Sheets rate limits** | Частота запросов | Превышение лимитов API |
| **SQLAlchemy N+1** | Запросы без `joinedload` | 50 запросов вместо 1 при загрузке билетов |
| **Блокирующие операции** | Синхронные вызовы в async | `time.sleep()` в обработчиках |

**Инструменты:**
- `cProfile` — профилирование по функциям
- Логи NATS — время обработки сообщений

**Критерий "аудит пройден":**
- Ответ бота ≤ 2 секунд
- Нет N+1 запросов в критических путях
- NATS-сообщения обрабатываются без задержек

## 🟡 Средний приоритет

<a id="type-hints"></a>
### 4. Аудит типизации (Type Hints Audit)

**Цель:** Убедиться, что код правильно типизирован.

**Что именно искать:**

| Категория | Паттерн поиска | Пример проблемы |
|-----------|----------------|-----------------|
| **Return type hints** | `def func():` без `->` | `def handle_payment(update, context):` без return type |
| **Dict[str, Any]** | Использование вместо dataclass | `context: Dict[str, Any]` вместо конкретного типа |
| **Optional/Union** | `None` без `Optional` | Параметр может быть `None`, но тип не отражает это |

**Критерий "аудит пройден":**
- Все публичные функции имеют return type hints
- `Dict[str, Any]` заменён на dataclass/TypedDict где возможно

---

<a id="api-design"></a>
### 5. Аудит API-дизайна (API Design Audit)

**Цель:** Проверить соответствие API лучшим практикам REST.

**Что именно искать:**

| Категория | Что проверять | Пример проблемы |
|-----------|---------------|-----------------|
| **HTTP-методы** | GET/POST/PUT/DELETE | GET с побочными эффектами |
| **Статус-коды** | 200/201/400/404/500 | 200 для ошибки |
| **Pydantic schemas** | Валидация входных данных | Отсутствие схем для сложных запросов |
| **Rate limiting** | Ограничение запросов | Нет middleware для rate limiting |

**Критерий "аудит пройден":**
- Все эндпоинты используют правильные HTTP-методы
- Ответы содержат корректные статус-коды
- Входные данные валидируются через Pydantic

---

<a id="frontend-architecture"></a>
### 6. Аудит Frontend-архитектуры (Frontend Architecture Audit)

**Цель:** Проверить качество веб-части (Jinja2 шаблоны, CSS).

**Что именно искать:**

| Категория | Что проверять | Пример проблемы |
|-----------|---------------|-----------------|
| **Jinja2 шаблоны** | DRY, макросы | Дублирование блоков в шаблонах |
| **CSS-архитектура** | Структура, специфичность | Inline-стили, !important |
| **Accessibility** | ARIA, семантика | Нет `aria-*`, `alt` у изображений |
| **Responsive design** | Media queries | Не адаптировано под мобильные |

**Критерий "аудит пройден":**
- Нет дублирования в шаблонах
- CSS организован по BEM или аналогичной методологии
- Базовая accessibility соблюдена

<a id="telegram-ui"></a>
### 7. Аудит Telegram UI (Telegram UI Audit)

**Цель:** Проверить качество интерфейса Telegram-бота.

**Что именно искать:**

| Категория | Что проверять | Пример проблемы |
|-----------|---------------|-----------------|
| **Inline-кнопки** | Callback data, лимиты | `callback_data` > 64 байта |
| **Клавиатуры** | DRY, навигация | Дублирование клавиатур |
| **Сообщения** | Длина, форматирование | > 4096 символов без разбиения |
| **Навигация** | Кнопки "Назад", "Отмена" | Отсутствуют в длинных диалогах |

**Критерий "аудит пройден":**
- Все клавиатуры используют `utl_kbd.py`
- Сообщения не превышают лимиты Telegram
- Навигация интуитивна

<a id="error-handling"></a>
### 8. Аудит обработки ошибок (Error Handling Audit)

**Цель:** Убедиться, что ошибки обрабатываются корректно.

**Что именно искать:**

| Категория | Что проверять | Пример проблемы |
|-----------|---------------|-----------------|
| **FastAPI exception handler** | Глобальная обработка | Нет `@app.exception_handler` |
| **ptb error handlers** | Обработка ошибок бота | Краш бота при ошибке |
| **NATS error callbacks** | Обработка ошибок воркеров | Потеря сообщения при ошибке |
| **Logging** | Именованные логгеры | `print()` вместо `logger.error()` |

**Критерий "аудит пройден":**
- Бот не крашится при ошибках
- Все ошибки логируются
- Пользователь получает понятное сообщение

**Цель:** Проверить локализацию и работу с датами.

<a id="solid"></a>
### 13. Аудит SOLID-принципов (SOLID Principles Audit)

**Цель:** Проверить соблюдение принципов SOLID и DRY.

**Что именно искать:**

| Принцип | Что проверять | Пример проблемы |
|---------|---------------|-----------------|
| **Single Responsibility** | Размер хендлеров | `reserve_hl.py` > 500 строк |
| **DRY** | Дублирование кода | Одна и та же логика в 2+ местах |
| **Цикломатическая сложность** | Сложность функций | Функция > 50 строк с вложенными условиями |

**Критерий "аудит пройден":**
- Хендлеры ≤ 200 строк
- Нет дублирования логики
- Цикломатическая сложность ≤ 10
