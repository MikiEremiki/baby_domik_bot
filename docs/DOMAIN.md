# Предметная область (Domain Guide)
## BabyDomikBot

Данный документ содержит описание предметной области и бизнес-процессов проекта **BabyDomikBot** — Telegram-бота и сопутствующих сервисов для управления театральными мероприятиями.

> **Словарь терминов** вынесен в [`docs/GLOSSARY.md`](GLOSSARY.md) — универсальный язык для общения между разработчиком и AI-агентом.

---

### 1. Назначение системы и бизнес-контекст

BabyDomikBot автоматизирует полный цикл управления театральными мероприятиями:

1. **Бронирование билетов через Telegram**:
   - Пользователь выбирает спектакль, дату и формат посещения (взрослый + ребёнок).
   - Бот формирует ссылку на оплату через YooKassa (СБП).
   - После оплаты билет подтверждается автоматически или администратором.
   - Данные о бронировании записываются в PostgreSQL и Google Sheets.

2. **Управление расписанием**:
   - Администраторы создают и редактируют сеансы спектаклей через команды `/update_*`.
   - Изменения расписания фиксируются в журнале `ScheduleChange` с снимками `before`/`after`.
   - Выгрузка в Google Sheets выполняется асинхронно через `/sync_schedule` с проверкой конфликтов.

3. **Оплата и фискализация**:
   - Платежи обрабатываются через YooKassa с перенаправлением на СБП.
   - Вебхуки от YooKassa приходят в FastAPI, публикуются в NATS и обрабатываются ботом.
   - Фискальные чеки получаются через YooKassa SDK (`src/api/receipt_service.py`): статус чека маппится из статуса платежа (succeeded→READY, pending→PENDING, canceled→CANCELED).
   - Администратор просматривает чек командой `/receipt`, отправляет его клиенту кнопкой «📤 Отправить клиенту».
   - Кнопка «🧾 Чек» доступна в уведомлении о платеже и сохраняется после confirm/reject.

4. **Заказные мероприятия и дни рождения**:
   - Отдельный поток для бронирования выездных мероприятий (`birthday_hl.py`).
   - Предоплаченные счета маршрутизируются в топик «Выездные мероприятия».

5. **Рассылки и уведомления**:
  - Массовая рассылка по продажам через NATS (`sales` → `sales_worker.py`).
  - Уведомления об ошибках Google Sheets через `gspread_failed`.
  - Админские топики для отчётов: «Списки на показы», «Лист ожидания», «Бронирования спектаклей».
  - Админские уведомления, списки на показы (`/list`), действие «Покупатель» и диалог переноса используют единый хелпер `format_ticket_contacts` (`src/utilities/utl_ticket.py`) для вывода контактов и источника из билета: `Источник: …` (Сайт/Бот), `Покупатель: @username Имя` или `Покупатель: Неизвестен`, `Телефон: +7…` или `не указан`, `Email: …` или `не указан`. Данные берутся из `Ticket.phone`, `Ticket.email`, `Ticket.source`.

6. **Авторассылки (Auto-sendings)**:
   - Шаблоны автоматических рассылок: напоминания перед сеансом, материалы после оплаты, запросы отзывов.
   - Триггеры: `EVENT` (относительно сеанса, по тик-расписанию каждые 3 минуты) и `PAYMENT` (после оплаты, через webhook).
   - Управление через админскую панель: CRUD в `auto_sending_hl.py`, ядро отправки в `schedule/auto_sending.py`.
   - Дедупликация через журнал `auto_sending_delivery` (UNIQUE по `dedup_key`).
   - Точный режим (precise) — отправка в точную минуту через `run_once` задачу.

### 2. Ключевые бизнес-процессы

#### 2.1 Бронирование билета

1. Пользователь запускает бота и выбирает спектакль.
2. Бот показывает доступные сеансы (`ScheduleEvent`) и форматы билетов (`BaseTicket`).
3. Пользователь выбирает дату, время и количество билетов.
4. Бот запрашивает email покупателя — он сохраняется в поле `Ticket.email` (не перезаписывает `User.email`). Email передаётся в платёж YooKassa для отправки чека.
5. Бот создаёт запись `Ticket` со статусом `CREATED`, источником `TicketSource` (`BOT` для бота, `WEBSITE` для сайта), email покупателя и телефоном покупки (`Ticket.phone`). Телефон — снимок на момент покупки; изменение `Adult.phone` или профиля пользователя после покупки не меняет `Ticket.phone`. При переносе билета `email` и `phone` исходного билета копируются в новый. Формируется платёж YooKassa.
6. После успешной оплаты статус меняется на `PAID`, затем на `APPROVED`.
7. Данные записываются в Google Sheets через NATS (`gspread_worker.py`).

#### 2.1.2 Перенос билета (`/migration_admin`)

Администратор переносит билет на другой сеанс: вводит ID билета, выбирает новый сеанс и формат (обычный или индивидуальный). Логика вынесена в `execute_ticket_migration` — общую функцию для обоих типов переноса.

**Обычный перенос:** админ выбирает готовый `BaseTicket`, цена берётся из шаблона.

**Индивидуальный перенос:** админ вводит `дети взрослые стоимость`, где `стоимость` — цена, заданная админом. Создаётся или используется существующий кастомный `BaseTicket`.

**Одна транзакция БД:** статус старого билета → `MIGRATED`, создание нового билета, привязка пользователя и людей — один `commit`. При ошибке — `rollback`, БД остаётся в исходном состоянии. Google Sheets обновляется только после успешного commit.

**Повторный перенос:** если исходный билет уже в статусе `MIGRATED`, новый не создаётся, бот сообщает «Билет уже перенесён».

**Валидация телефона на сайте:** при бронировании через сайт (`POST /booking/{schedule_id}`) номер телефона очищается, обрезается до последних 10 цифр, затем проверяется `check_phone_number` (только номера РФ: `9XXXXXXXXX`). При невалидном номере — ошибка формы: «Проверьте правильность 10 цифр после +7/8, определено: {phone}».

#### 2.1.1 Админское бронирование (`/reserve_admin`)

После выбора билета администратор проходит шаг `EMAIL` — вводит email покупателя (предзаполняется из профиля, но может быть изменён). Email сохраняется только в контексте бронирования, не перезаписывая профиль администратора. Без email создание ссылки на оплату заблокировано: бот вернёт к шагу ввода email с сообщением «Для создания ссылки на оплату необходим email покупателя». Цепочка шагов: `TICKET`/`CUSTOM_TICKET_PARAMS` → `EMAIL` → `FORMA` → `PHONE` → `CHILDREN` → `CONFIRM_RESERVATION`.

#### 2.2 Синхронизация данных

- **Из Google Sheets в БД:** `/update_places`, `/update_schedule_event_data` (остальные команды `/update_*` из COMMAND_DICT больше не зарегистрированы, см. `reports/2026-10-11_command-dict-audit.md`).
- **Из БД в Google Sheets:** `/sync_schedule [event_id]` с проверкой конфликтов.
- Обратный импорт `/update_schedule_event_data` защищает сеансы с несинхронизированными правками от затирания.

#### 2.3 Управление промокодами и скидками

- Промокоды хранятся в модели `Promotions`.
- Расчёт цен с учётом промокодов выполняется в `booking_service.py`.
- Типы цен: `weekday` / `weekend` (`TicketPriceType`).

### 3. Роли пользователей

| Роль | Описание | Доступ |
|------|----------|--------|
| **Пользователь** | Telegram-пользователь, бронирующий билеты. | Бронирование, просмотр билетов (`/tickets`). |
| **Администратор (root/super_admin)** | Сотрудник театра из `ADMIN_ID` / `SUPERADMIN_CHAT_ID` (`settings.py`), управляющий расписанием и бронированиями. | Полный доступ к командам и разделам `/settings`, выдача прав другим. |
| **Сотрудник с частичным доступом** | Пользователь, что-то из команд или разделов которого разрешено записями в `user_command_access` (ключи `list`, `send_msg`, `settings:<section>`…). | Только выданное; права выдаются и забираются через `/settings` → «База данных» → «Доступ к командам» без деплоя. Подробности: [`docs/COMMANDS.md`](COMMANDS.md). |
| **Разработчик** | Технический специалист, получающий уведомления об ошибках. | Уведомления `gspread_failed`, логи. |

> **После деплоя:** раздел «Расписание» в `/settings` больше не выдаётся хардкодом — root выдаёт Кочетковой право `settings:schedule_event` через UI.
