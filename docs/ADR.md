### <a name="adr-001"></a> ADR-001: Выбор python-telegram-bot для Telegram-бота

- **Статус:** Принято.
- **Контекст:** Проект требует Telegram-бота с поддержкой сложных диалогов (бронирование билетов, дни рождения, заказные мероприятия), клавиатур и middleware.
- **Решение:** 
  - Использовать `python-telegram-bot` (ptb) как основной фреймворк для Telegram-бота.
  - `ConversationHandler` для управления состоянием диалогов, состояния в `src\conv_hl\`.
  - Бизнес-логика в `src\handlers\`, регистрация в `src\handlers\set_handlers.py`.
  - Middleware для сквозной обработки: БД, глобальный переключатель, статус пользователя, проверка бронирования, логирование.
- **Последствия:** Полная поддержка асинхронности, типизация, встроенные middleware и фильтры. Разделение состояний и логики обеспечивает читаемость и тестируемость.

### <a name="adr-002"></a> ADR-002: NATS как брокер сообщений между сервисами

- **Статус:** Принято.
- **Контекст:** Проект состоит из нескольких независимых сервисов: Telegram-бот, FastAPI (вебхуки YooKassa), фоновые воркеры (Google Sheets, рассылки). Нужен надёжный канал связи между ними.
- **Решение:** 
  - Использовать NATS с JetStream для персистентных сообщений.
  - FastAPI публикует вебхуки YooKassa в тему `yookassa`.
  - Бот подписывается на `yookassa`, `gspread_failed`, `sales_report`, `schedule_sync_result`.
  - Воркеры подписываются на `gspread` и `sales`.
  - FastStream для упрощения работы с NATS в Python.
- **Последствия:** Слабая связность между сервисами, устойчивость к перезапускам (JetStream), масштабируемость. Добавлена сложность инфраструктуры (NATS-сервер в Docker Compose).

### <a name="adr-003"></a> ADR-003: SQLAlchemy с lazy='raise' для явной загрузки

- **Статус:** Принято.
- **Контекст:** Проект использует SQLAlchemy для работы с PostgreSQL. По умолчанию ленивая загрузка может приводить к N+1 проблемам и непредсказуемым запросам.
- **Решение:** 
  - Использовать `lazy='raise'` для всех отношений моделей.
  - Явно указывать `joinedload`/`selectinload` при необходимости загрузки связанных сущностей.
  - Все CRUD-операции в `src\db\db_postgres.py` с явными запросами.
- **Последствия:** Полный контроль над запросами к БД, отсутствие скрытых N+1 проблем. Требуется внимательность при написании запросов.

### <a name="adr-004"></a> ADR-004: FastAPI для вебхуков и веб-интерфейса

- **Статус:** Принято.
- **Контекст:** Проект требует обработки вебхуков от YooKassa, авторизации через Telegram Login Widget и отрисовки HTML-страниц (афиша, события, студия).
- **Решение:** 
  - FastAPI как единый веб-сервис для всех HTTP-запросов.
  - Роутеры в `src\api\web\routes\`: `api.py` (вебхуки), `auth.py` (Telegram Login), `booking.py` (бронирование), `pages.py` (HTML-страницы).
  - Pydantic схемы для валидации данных API.
  - Jinja2 для HTML-шаблонов (`templates/`).
- **Последствия:** Единая точка входа для HTTP, асинхронность, автоматическая валидация через Pydantic. Веб-интерфейс и API объединены в один сервис.

### <a name="adr-005"></a> ADR-005: Асинхронная запись в Google Sheets через NATS

- **Статус:** Принято.
- **Контекст:** Google Sheets используется как legacy-хранилище для резервов, клиентской базы и расписания. Прямые синхронные вызовы блокируют обработчики и подвержены таймаутам.
- **Решение:** 
  - Все операции записи публикуются в тему `gspread` через NATS.
  - `gspread_worker.py` подписывается на тему и выполняет физическую запись.
  - Ошибки записи публикуются в `gspread_failed` для уведомления администратора.
  - Чтение данных выполняется синхронно через `/update_*` команды.
- **Последствия:** Неблокирующие операции, устойчивость к таймаутам Google Sheets, отслеживание ошибок. Добавлена задержка между публикацией и фактической записью.

### <a name="adr-006"></a> ADR-006: Изоляция сервисов по зависимостям

- **Статус:** Принято.
- **Контекст:** Проект развёртывается в отдельных Docker-контейнерах (бот, FastAPI, воркеры). Каждый контейнер имеет свой набор зависимостей.
- **Решение:** 
  - FastAPI и воркеры не импортируют модули с зависимостями от `python-telegram-bot` или `gspread`.
  - Общие утилиты (`src\utilities\utl_text.py`, `src\utilities\utl_place.py`) не зависят от внешних сервисов.
  - Запрещено использовать `if TYPE_CHECKING:` для сокрытия межсервисных зависимостей.
- **Последствия:** Чистое разделение контейнеров, независимая сборка и развёртывание. Требуется дисциплина при добавлении новых модулей.

### <a name="adr-007"></a> ADR-007: Docker Compose с профилями для развёртывания

- **Статус:** Принято.
- **Контекст:** Проект состоит из нескольких сервисов (бот, FastAPI, NATS, PostgreSQL, воркеры), которые могут запускаться независимо.
- **Решение:** 
  - Docker Compose с профилями: `migration` (только миграции), `bot` (только бот), `all` (полный стек).
  - Отдельные Dockerfile для каждого сервиса: `Dockerfile`, `Dockerfile-fastapi`, `Dockerfile-gspread`, `Dockerfile-migration`, `Dockerfile-sales`.
  - nginx как reverse proxy для внешнего трафика.
- **Последствия:** Гибкое развёртывание, возможность запуска отдельных сервисов для разработки. Сложность управления профилями.

### <a name="adr-008"></a> ADR-008: Jinja2 для веб-шаблонов без бандлера

- **Статус:** Принято.
- **Контекст:** Веб-интерфейс проекта включает несколько HTML-страниц (главная, афиша, события, студия, заказные мероприятия). Не требуется сложная клиентская логика.
- **Решение:** 
  - Jinja2 для серверного рендеринга HTML (`templates/`).
  - Статические файлы (CSS, изображения) в `static/`.
  - Отсутствие бандлера (npm, Webpack, Vite) — минимальная клиентская логика.
- **Последствия:** Простота разработки и развёртывания, нет зависимости от Node.js. Ограниченная интерактивность на клиенте.
