### <a name="adr-009"></a> ADR-009: Улучшение надёжности авторассылок

- **Статус:** Принято.
- **Контекст:** После реализации ядра авторассылок (тикеты 01–06, план `unify-auto-sendings`) выявлены три области для улучшения надёжности: задержка отправки до 5 минут, отсутствие retry-механизма при ошибках отправки, и отсутствие структурированных метрик.
- **Решение:**
  - **Интервал тика:** Уменьшен с 5 минут (300 сек) до 3 минут (180 сек). Catch-up window соответствует интервалу тика.
  - **Retry при ошибке:** Если отправка не удалась, запись в журнал `auto_sending_delivery` не создаётся — следующий тик автоматически повторит попытку. Лимит попыток не установлен, так как количество пользователей на сеанс мало (3–10 человек).
  - **Структурированное логирование:** Каждая критическая ошибка отправки логируется отдельно через `logging` с `extra` параметрами (user_id, auto_sending_id, error_type, error_message). Ожидаемые ошибки (Forbidden, RetryAfter) не логируются как критические.
- **Последствия:** Задержка отправки уменьшена до 3 минут, ошибки отправки автоматически повторяются, метрики позволяют отслеживать проблемы без шума от ожидаемых ошибок. Не требует миграции БД или новых зависимостей.

### <a name="adr-010"></a> ADR-010: Фискальные чеки через YooKassa SDK

- **Статус:** Принято.
- **Контекст:** После оплаты через YooKassa администраторам и клиентам нужен доступ к фискальному чеку. Ранее чек формировался через отдельный PowerShell-скрипт `Get-YooKassaReceipt.ps1`, что не было интегрировано в бота.
- **Решение:**
  - **Чистый сервисный слой** (`src/api/receipt_service.py`) — бизнес-логика получения чека без зависимости от Telegram: `ReceiptStatus` (StrEnum: READY, PENDING, CANCELED, NO_PAYMENT, NOT_FOUND, API_ERROR), `ReceiptInfo` (dataclass с фискальными данными), `get_ticket_receipt(session, ticket_id)` — маппинг статусов платежа на статус чека.
  - **YooKassa SDK обёртка** (`src/api/yookassa_connect.py`) — `fetch_payment_receipts(payment_id, timeout)` вызывает `Receipt.list` через `asyncio.to_thread` + `wait_for(10s)`, `build_ofd_url(fn, fp, i)` формирует публичную ссылку OFD.
  - **Админская команда** (`/receipt`) — отправляет карточку чека с фискальными данными и кнопкой OFD-ссылки.
  - **Кнопка «🧾 Чек»** — добавлена в уведомление о платеже (webhook) и persists после confirm/reject.
  - **Отправка клиенту** — кнопка «📤 Отправить клиенту» отправляет ссылку на чек в чат клиента с обработкой `Forbidden` (клиент заблокировал бота).
- **Последствия:** Администраторы могут просмотреть чек по билету, отправить его клиенту, и кнопка чека доступна прямо в уведомлении о платеже. Не требует миграции БД, использует существующие модели Ticket и Payment. Изоляция сервисов соблюдена: `receipt_service.py` не импортирует `python-telegram-bot`.

### <a name="adr-001"></a> ADR-001: Выбор python-telegram-bot для Telegram-бота

- **Статус:** Принято.
- **Контекст:** Проект требует Telegram-бота с поддержкой сложных диалогов (бронирование билетов, дни рождения, заказные мероприятия), клавиатур и middleware.
- **Решение:** 
  - Использовать `python-telegram-bot` (ptb) как основной фреймворк для Telegram-бота.
  - `ConversationHandler` для управления состоянием диалогов, состояния в `src\conv_hl\`.
  - Бизнес-логика в `src\handlers\`, регистрация в `src\setup_bot_handlers.py`.
  - Middleware для сквозной обработки: БД, глобальный переключатель, статус пользователя, проверка бронирования, логирование.
- **Последствия:** Полная поддержка асинхронности, типизация, встроенные middleware и фильтры. Разделение состояний и логики обеспечивает читаемость и тестируемость.

### <a name="adr-002"></a> ADR-002: NATS как брокер сообщений между сервисами

- **Статус:** Принято.
- **Контекст:** Проект состоит из нескольких независимых сервисов: Telegram-бот, FastAPI (вебхуки YooKassa), фоновые воркеры (Google Sheets, рассылки). Нужен надёжный канал связи между ними.
- **Решение:** 
  - Использовать NATS с JetStream для персистентных сообщений.
  - FastAPI публикует вебхуки YooKassa в тему `yookassa`.
  - Бот подписывается на `yookassa`, `gspread_failed`, `sales_report`, `schedule_sync_result`.
  - Воркеры подписываются на `gspread` и `sales`.
  - FastStream для упрощения работы с NATS в Python.
- **Последствия:** Слабая связность между сервисами, устойчивость к перезапускам (JetStream), масштабируемость. Добавлена сложность инфраструктуры (NATS-сервер в Docker Compose).

### <a name="adr-003"></a> ADR-003: SQLAlchemy с lazy='raise' для явной загрузки

- **Статус:** Принято.
- **Контекст:** Проект использует SQLAlchemy для работы с PostgreSQL. По умолчанию ленивая загрузка может приводить к N+1 проблемам и непредсказуемым запросам.
- **Решение:** 
  - Использовать `lazy='raise'` для всех отношений моделей.
  - Явно указывать `joinedload`/`selectinload` при необходимости загрузки связанных сущностей.
  - Все CRUD-операции в `src\db\db_postgres.py` с явными запросами.
- **Последствия:** Полный контроль над запросами к БД, отсутствие скрытых N+1 проблем. Требуется внимательность при написании запросов.

### <a name="adr-004"></a> ADR-004: FastAPI для вебхуков и веб-интерфейса

- **Статус:** Принято.
- **Контекст:** Проект требует обработки вебхуков от YooKassa, авторизации через Telegram Login Widget и отрисовки HTML-страниц (афиша, события, студия).
- **Решение:** 
  - FastAPI как единый веб-сервис для всех HTTP-запросов.
  - Роутеры в `src\api\web\routes\`: `api.py` (вебхуки), `auth.py` (Telegram Login), `booking.py` (бронирование), `pages.py` (HTML-страницы).
  - Pydantic схемы для валидации данных API.
  - Jinja2 для HTML-шаблонов (`templates/`).
- **Последствия:** Единая точка входа для HTTP, асинхронность, автоматическая валидация через Pydantic. Веб-интерфейс и API объединены в один сервис.

### <a name="adr-005"></a> ADR-005: Асинхронная запись в Google Sheets через NATS

- **Статус:** Принято.
- **Контекст:** Google Sheets используется как legacy-хранилище для резервов, клиентской базы и расписания. Прямые синхронные вызовы блокируют обработчики и подвержены таймаутам.
- **Решение:** 
  - Все операции записи публикуются в тему `gspread` через NATS.
  - `gspread_worker.py` подписывается на тему и выполняет физическую запись.
  - Ошибки записи публикуются в `gspread_failed` для уведомления администратора.
  - Чтение данных выполняется синхронно через `/update_*` команды.
- **Последствия:** Неблокирующие операции, устойчивость к таймаутам Google Sheets, отслеживание ошибок. Добавлена задержка между публикацией и фактической записью.

### <a name="adr-006"></a> ADR-006: Изоляция сервисов по зависимостям

- **Статус:** Принято.
- **Контекст:** Проект развёртывается в отдельных Docker-контейнерах (бот, FastAPI, воркеры). Каждый контейнер имеет свой набор зависимостей.
- **Решение:** 
  - FastAPI и воркеры не импортируют модули с зависимостями от `python-telegram-bot` или `gspread`.
  - Общие утилиты (`src\utilities\utl_text.py`, `src\utilities\utl_place.py`) не зависят от внешних сервисов.
  - Запрещено использовать `if TYPE_CHECKING:` для сокрытия межсервисных зависимостей.
- **Последствия:** Чистое разделение контейнеров, независимая сборка и развёртывание. Требуется дисциплина при добавлении новых модулей.

### <a name="adr-007"></a> ADR-007: Docker Compose с профилями для развёртывания

- **Статус:** Принято.
- **Контекст:** Проект состоит из нескольких сервисов (бот, FastAPI, NATS, PostgreSQL, воркеры), которые могут запускаться независимо.
- **Решение:** 
  - Docker Compose с профилями: `migration` (только миграции), `bot` (только бот), `all` (полный стек).
  - Отдельные Dockerfile для каждого сервиса: `Dockerfile`, `Dockerfile-fastapi`, `Dockerfile-gspread`, `Dockerfile-migration`, `Dockerfile-sales`.
  - nginx как reverse proxy для внешнего трафика.
- **Последствия:** Гибкое развёртывание, возможность запуска отдельных сервисов для разработки. Сложность управления профилями.

### <a name="adr-008"></a> ADR-008: Jinja2 для веб-шаблонов без бандлера

- **Статус:** Принято.
- **Контекст:** Веб-интерфейс проекта включает несколько HTML-страниц (главная, афиша, события, студия, заказные мероприятия). Не требуется сложная клиентская логика.
- **Решение:** 
  - Jinja2 для серверного рендеринга HTML (`templates/`).
  - Статические файлы (CSS, изображения) в `static/`.
  - Отсутствие бандлера (npm, Webpack, Vite) — минимальная клиентская логика.
- **Последствия:** Простота разработки и развёртывания, нет зависимости от Node.js. Ограниченная интерактивность на клиенте.

### <a name="adr-011"></a> ADR-011: Ограничение доступа к детям в бронировании по user_id

- **Статус:** Принято.
- **Контекст:** При бронировании через бота обычные пользователи могли видеть детей, не привязанных к их аккаунту, через фильтры «По имени» и «По возрасту». Функции `search_children` и `get_children_by_phone` в `src/db/db_postgres.py` искали по всей базе без фильтрации по `user_id`. Дополнительно, операции удаления и редактирования детей (`CHLD_DEL`, `CHLD_EDIT_START`) принимали ID без проверки принадлежности, а сохранённый список выбранных детей мог содержать ранее выданные чужие записи.
- **Решение:**
  - **Фильтрация на уровне БД:** `search_children` и `get_children_by_phone` в `src/db/db_postgres.py` дополнены параметрами `user_id` и `admin_mode`. Для обычных пользователей (`admin_mode=False`) поиск ограничен записями с `Person.user_id == user_id`. Администраторы (`admin_mode=True`) сохраняют неограниченный поиск по всей базе, включая детей с сайта без `user_id`.
  - **Проверка прав администратора:** `_update_children` в `src/handlers/reserve/common.py` проверяет права через `permissions.can_or_false(user_id, 'RESERVE_ADMIN', session)` вместо проверки подстроки `_admin` в команде. Ошибка проверки прав — отказ в расширенном доступе.
  - **Защита от устаревших данных:** В `src/handlers/reserve/input.py` добавлены `_is_admin_mode` и `_is_child_accessible` для проверки принадлежности ребенка перед удалением, редактированием, выбором и подтверждением. Недоступные ID отклоняются, устаревший выбор очищается.
  - **Тесты:** Расширены существующие тесты в `test/test_reserve_admin_improvements.py` и `test/test_reserve_refactor.py`: два аккаунта с одинаковыми именами/возрастами, совпадающий и чужой телефон, ребёнок без `user_id`, отсутствие результатов и fallback.
- **Последствия:** Обычные пользователи видят только своих детей во всех режимах фильтрации. Дети, созданные на сайте без `user_id`, не отображаются в боте — это сознательный шаг, так как совпадение телефона не является доказательством принадлежности. Механизм привязки таких детей будет реализован отдельно. Администраторы сохраняют полный доступ ко всем записям. Не требует миграции БД.

### <a name="adr-012"></a> ADR-012: Схема в Alembic, перенос исторических данных — ручными SQL вне цепочки миграций

- **Статус:** Принято.
- **Контекст:** При добавлении поля `TicketSource` (источник покупки билета: сайт/бот) потребовалось заполнить исторические данные — классифицировать уже существующие билеты по маркерам в `notes`. Включение такой логики в Alembic-миграцию нарушает принцип «миграция = только схема» и делает миграцию неидемпотентной.
- **Решение:**
  - **Схема БД** — только ревизиями Alembic (`src/db/migrations/versions/`). Ревизия создаёт тип `ticket_source` и колонку `tickets.source`, не читает `manual_migrations`, не делает backfill.
  - **Перенос исторических данных** — отдельными SQL-скриптами в `src/db/migrations/manual/` (каталог вне `versions/`: Alembic берёт ревизии только из `versions/`). Скрипт работает в одной транзакции, создаёт таблицу `manual_migrations` (`CREATE TABLE IF NOT EXISTS`), классифицирует записи и оставляет маркер выполнения. Повторный запуск безопасен (идемпотентен).
  - **Проверка** — вручную проверяем таблицу `manual_migrations` в БД. Скрипт проверки не используется.
- **Последствия:** Чистая БД требует только `alembic upgrade head`. Для рабочей БД порядок: `alembic upgrade head` → ручной SQL → проверка. Ручные скрипты не влияют на цепочку и нумерацию миграций. Таблица `manual_migrations` нужна только для ручных скриптов и создаётся ими же.

### <a name="adr-013"></a> ADR-013: Перенос билета одной транзакцией

- **Статус:** Принято.
- **Контекст:** Перенос билета (`/migration_admin`) ранее выполнялся последовательными операциями: обновление статуса старого билета с commit, возврат мест в Google Sheets, создание нового билета с commit, привязка пользователя с commit. При сбое на любом этапе БД могла остаться в неконсистентном состоянии, а ручной откат статуса требовал дополнительного кода.
- **Решение:**
  - **Одна транзакция БД:** `execute_ticket_migration` в `src/handlers/reserve_admin_hl.py` выполняет три операции — статус старого билета → `MIGRATED`, создание нового билета (`create_transferred_ticket`), привязка пользователя и людей (`attach_user_and_people_to_ticket`) — одним `commit`. При любой ошибке — `rollback`, БД остаётся в исходном состоянии.
  - **Параметр `auto_commit`** в `db_postgres.create_ticket`, `db_postgres.update_ticket`, `db_postgres.attach_user_and_people_to_ticket` и `update_ticket_db_and_gspread` позволяет отложить commit. По умолчанию `auto_commit=True` — поведение в остальных местах не меняется. В `update_ticket_db_and_gspread` параметр `auto_commit` является keyword-only (после `*`).
  - **Google Sheets после commit:** статус старого билета и свободные места (`increase_free_seat`) обновляются только после успешного commit БД. Если транзакция откатилась, разработчику уходит уведомление об откате в Google Sheets вручную.
  - **Отказ от ручного отката:** повторный вызов `update_ticket_db_and_gspread` со старым статусом при ошибке удалён — при rollback БД уже в исходном состоянии, откат не нужен.
  - **Повторный перенос:** если исходный билет уже `MIGRATED`, новый не создаётся, бот сообщает «Билет уже перенесён». Достаточно проверки статуса, блокировка строки (`SELECT … FOR UPDATE`) не нужна.
  - **Общая функция:** `execute_ticket_migration` используется и для обычного, и для индивидуального переноса. Индивидуальный перенос подключён через `CUSTOM_TICKET_PARAMS` в `migration_admin_conv_hl.py`.
- **Последствия:** Перенос билета стал атомарным — БД всегда консистентна. Google Sheets может рас расходиться с БД при сбое сети, но расхождения правятся вручную. Код переноса упрощён: вместо двух дублирующих веток (обычный/индивидуальный) — одна функция. Не требует миграции БД.
